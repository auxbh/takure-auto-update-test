# Setting up code signing for the auto-updater

The auto-updater verifies every downloaded `takure.dll` in two independent ways before it's
allowed to replace the currently running hook:

1. **SHA-256 checksum** against the value published in `update.json`.
2. **Authenticode signature + public key pinning** — the downloaded DLL must carry a valid
   Authenticode signature, and the signer's public key must exactly match the `PUBLIC_KEY`
   constant baked into the binary at compile time.

Step 2 is what actually protects you: even if an attacker compromises GitHub Pages or the
release artifacts and serves a malicious DLL with a matching (self-consistent) checksum, they
can't forge a signature that matches your pinned public key without your private key.

You do **not** need a certificate from a paid CA for this — a self-signed certificate works
fine, since we never rely on Windows' certificate trust chain. We only ever compare the raw
public key bytes.

This document walks through generating that certificate, wiring it into the release pipeline,
and configuring the GitHub side (Pages + secrets) end to end.

## 1. Generate a self-signed code-signing certificate

Run this in PowerShell (does not need to be elevated):

```powershell
$cert = New-SelfSignedCertificate `
    -Type CodeSigning `
    -Subject "CN=YourName, O=YourOrg" `
    -KeyAlgorithm RSA `
    -KeyLength 2048 `
    -HashAlgorithm SHA256 `
    -KeyUsage DigitalSignature `
    -NotAfter (Get-Date).AddYears(10) `
    -CertStoreLocation Cert:\CurrentUser\My `
    -KeyExportPolicy Exportable
```

Adjust `-Subject` to whatever you like — it's not checked by anything, it's just metadata.

Note the thumbprint it prints out (`$cert.Thumbprint`), you'll need it below.

## 2. Export the certificate + private key to a PFX

```powershell
& {
    $password = ConvertTo-SecureString -String "<PASSWORD>" -Force -AsPlainText
    Export-PfxCertificate -Cert $cert -FilePath .\takure_signing.pfx -Password $password
}
```

Replace `"<PASSWORD>"` with a strong password.

`*.pfx` is already gitignored in this repo — double check with `git status` that it never gets
staged. This file is your private signing key; treat it like a secret.

## 3. Extract the public key and embed it in `consts.rs`

`RSACryptoServiceProvider` on older .NET Framework doesn't expose a convenient
`ExportRSAPublicKey()`, so we manually DER-encode the PKCS#1 `RSAPublicKey` structure from the
raw modulus/exponent. Run this in PowerShell, replacing the thumbprint with the one from step 1:

```powershell
& {
    function ConvertTo-Asn1Length {
        param([int]$Length)
        if ($Length -lt 0x80) {
            return [byte[]]@($Length)
        }
        $lenBytes = @()
        $temp = $Length
        while ($temp -gt 0) {
            $lenBytes = ,([byte]($temp -band 0xFF)) + $lenBytes
            $temp = $temp -shr 8
        }
        return ,([byte](0x80 -bor $lenBytes.Length)) + $lenBytes
    }

    function ConvertTo-Asn1Integer {
        param([byte[]]$Bytes)
        $b = $Bytes
        $i = 0
        while ($i -lt ($b.Length - 1) -and $b[$i] -eq 0) { $i++ }
        $b = $b[$i..($b.Length - 1)]
        if ($b[0] -band 0x80) {
            $b = ,[byte]0x00 + $b
        }
        return ,0x02 + (ConvertTo-Asn1Length -Length $b.Length) + $b
    }

    $cert = Get-Item "Cert:\CurrentUser\My\<THUMBPRINT>"
    $rsa = [System.Security.Cryptography.X509Certificates.RSACertificateExtensions]::GetRSAPublicKey($cert)
    $params = $rsa.ExportParameters($false)

    $modulusDer = ConvertTo-Asn1Integer -Bytes $params.Modulus
    $exponentDer = ConvertTo-Asn1Integer -Bytes $params.Exponent
    $content = $modulusDer + $exponentDer
    $pubKeyDer = ,0x30 + (ConvertTo-Asn1Length -Length $content.Length) + $content

    $lines = for ($i = 0; $i -lt $pubKeyDer.Length; $i += 16) {
        $chunk = $pubKeyDer[$i..([Math]::Min($i + 15, $pubKeyDer.Length - 1))]
        "    " + (($chunk | ForEach-Object { "0x{0:x2}" -f $_ }) -join ", ") + ","
    }

    Write-Output "pub const PUBLIC_KEY: [u8; $($pubKeyDer.Length)] = ["
    $lines
    Write-Output "];"
}
```

Paste the resulting output into `src/consts.rs`, replacing the existing `PUBLIC_KEY` constant:

```rust
#[cfg(feature = "autoupdate")]
pub const PUBLIC_KEY: [u8; N] = [
    // ... generated bytes ...
];
```

(`N` will typically be 270 for a 2048-bit RSA key, but let the script tell you the real number —
don't hardcode 270.)

## 4. Point `consts.rs` at your GitHub repo

Still in `src/consts.rs`, update:

```rust
pub const UPDATE_REPO: &str = "yourname/yourrepo";

#[cfg(feature = "autoupdate")]
pub const UPDATE_MANIFEST_URL: &str = "https://yourname.github.io/yourrepo/update.json";
```

`UPDATE_REPO` is used to build the release download URL
(`github.com/<repo>/releases/download/v<version>/<asset>`), and `UPDATE_MANIFEST_URL` must point
at wherever `update.json` will be published via GitHub Pages (step 6).

## 5. Enable GitHub Pages on the repo

1. Go to the repo on GitHub → **Settings → Pages**.
2. Under **Build and deployment → Source**, select **GitHub Actions** (not "Deploy from a
   branch"). The release workflow deploys directly via `actions/deploy-pages`, it doesn't need a
   `gh-pages` branch.

## 6. Allow the release tag to deploy to the `github-pages` environment

By default, the built-in `github-pages` environment only allows deploys from specific branches,
not tags — which is exactly what the release workflow uses (`push: tags: ["v*.*.*"]`). If you
skip this step, the workflow will fail with:

```
Tag "vX.Y.Z" is not allowed to deploy to github-pages due to environment protection rules.
```

Fix it:

1. **Settings → Environments → github-pages**.
2. Under **Deployment branches and tags**, change the dropdown to **Selected branches and
   tags**.
3. Click **Add deployment branch or tag rule**, choose **Tag**, and add the pattern `v*`.
4. Save.

## 7. Add the signing secrets to the repo

The release workflow reads two secrets: the PFX file (base64-encoded) and its password.

Base64-encode the PFX:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path .\takure_signing.pfx))) | Set-Clipboard
```

This copies the base64 blob straight to your clipboard.

Then in the repo: **Settings → Secrets and variables → Actions → New repository secret**, and
add:

| Name | Value |
|---|---|
| `TAKURE_SIGNING_KEY_PFX_BASE64` | paste the clipboard contents from above |
| `TAKURE_SIGNING_KEY_PASSWORD` | the password you chose in step 2 |

## 8. Commit, tag, and release

```powershell
git add src/consts.rs
git commit -m "Point at yourname/yourrepo, embed signing public key"
git push

git tag v0.1.0
git push origin v0.1.0
```

Pushing the tag triggers `.github/workflows/release.yml`, which builds both architectures,
signs each `takure.dll` with `signtool` using the PFX secret, zips them into
`takure_32.zip`/`takure_64.zip`, publishes them as a GitHub Release, and deploys `update.json` to
GitHub Pages.

## 9. Verify

- Check the Actions tab — the release job should finish green.
- Check the repo's **Releases** page for `takure_32.zip` / `takure_64.zip`.
- Open `https://yourname.github.io/yourrepo/update.json` in a browser — it should show the
  version/commit/checksum JSON.
- Run an older build with `auto_update = true` in `takure.toml` and confirm the console log
  shows `Checking for updates...` → `Downloading update vX.Y.Z...` → a relaunch into the new
  version.

## Notes

- Never commit `takure_signing.pfx` — it's gitignored, but double-check `git status` before any
  commit that touches signing-related files.
- If you ever suspect the private key leaked, generate a new certificate, re-extract the public
  key, update `PUBLIC_KEY` in `consts.rs`, and cut a new release signed with the new key. Old
  clients pinned to the old key simply won't accept updates signed with the new one until they
  update through some other channel (e.g. a manual reinstall) — plan for that if it ever happens.
